# 给下一个 Codex 的交接

## 开始前

1. 读取根目录 `AGENTS.md`、`README.md`、`docs/PROJECT.md`。
2. 检查当前分支、工作区未提交变更和远程最新提交。不要覆盖用户或另一个账号正在做的工作。
3. 按任务读取 `dist/app.js`、`dist/data.js` 及相关演示。历史聊天不是必需依赖；仓库文档与当前代码提供上下文。
4. 读取 `docs/runs.md`、`docs/verification.md`，区分完成事实与待办。

## 新增一个案例

- 先比较已有案例，写明新增的设计做法或取舍。优先用户指定案例。
- 实际访问官方材料和源码；只描述已核实的实现。链接无法访问就记录，不能补编来源。
- 先建立整站地图，再写视觉、交互、源码阅读路径与局限。避免泛泛称赞“简洁”“现代”。
- 在 `dist/demos/` 添加局部演示，在 `dist/data.js` 增加案例；说明复现范围与原项目差异。
- 新增第二案例前处理 `docs/PROJECT.md` 列出的硬编码统计和编号。
- 不合格草稿不要放进 `ATLAS_CASES`，当前渲染器会显示数组内所有案例。跳过时写入运行记录。

## 修改网站功能

- 先描述具体触发条件和预期行为，再定位对应文件与函数。
- 保留原有hash链接、相对资源路径和浅色文档体验。跨架构迁移需有实际任务理由。
- 演示复现与原项目事实分别维护；改演示不能自动变成对原项目实现的结论。
- 检查搜索、主题筛选、空状态、案例与章节切换、演示控件和源码下载。
- 实际测试电脑和平板宽度下的正文、表格、代码块和触控入口。不能用“写了媒体查询”代替运行验证。

## 验证与提交

```sh
node scripts/check.mjs
```

该命令只验证部分静态结构与语法。依据修改补充必要浏览器检查；网络或浏览器不可用时，报告验证缺口，不能宣称自动收录标准全部通过。纯文档修改核对路径、字段和命令即可，不必重复完整界面测试。

使用独立任务分支。多个账号错开处理共享文件，合并前检查最新main。不要强推或重写他人提交；没有必要不引入新依赖。完成后更新相关文档和运行记录。根据本次用户授权提交或建立PR，不擅自宣称合并或发布成功。

## 两个可直接使用的任务

### 先整理可扩展性

> 读取 AGENTS.md、docs/PROJECT.md 和 docs/HANDOFF.md。检查当前首版，优先修复案例数量、覆盖问题数、演示数及详情编号的硬编码，使新增案例无需手工改统计。保持原有设计与链接，验证空状态和多案例渲染，在独立分支提交改动并说明验证结果。

### 继续积累案例

> 读取 AGENTS.md、docs/PROJECT.md、docs/HANDOFF.md 和 docs/automation.md，完成一次案例研究。首选整站导航、信息层级或阅读布局，与现有VitePress案例有明确差异。实际核查官方来源和源码，添加中文分析及原生交互演示，通过内容与交互检查后再收录；无法通过则记录原因。不要为更新频率凑数量。

## 状态交接格式

每次结束写清：修改了什么、为何修改、改动文件、已运行的检查、未验证项、提交或PR、部署状态、下一步。只在确有任务ID和验证证据时写“自动化已启用”。
